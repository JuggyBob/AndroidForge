# AndroidForge v0.13.0 — Optional Maestro, Tool Database & Complete MCP Surface

AndroidForge v0.13.0 is the next stable pre-1.0 release. It keeps the truthful verification layer from
v0.12 and adds optional Maestro installation, a searchable desktop command database, a complete MCP
tool surface, a compatibility policy and a security-hardening pass.

> **Stable status.** This is a normal GitHub release, not a prerelease. Windows is the tested host.
> Physical-device Maestro flows, instrumentation, snapshot restore and root-only operations remain
> incompletely validated. See **Known limitations** below.

## Highlights

### Optional Maestro, installed deliberately

Maestro is optional — native `androidforge ui` commands never require it. When a project has Maestro
flows, AndroidForge can install a pinned, verified build:

```powershell
androidforge tools install maestro --dry-run --json
androidforge tools install maestro --yes --json
androidforge tools status maestro --json
androidforge tools uninstall maestro --yes --json
```

- Pinned **Maestro CLI 2.12.1** from the official `cli-2.12.1/maestro.zip`.
- SHA-256 verified before extraction:
  `54dbb0716425626604973cbb374c585ca30272375d9ce15177a1152765ddd9d7`.
- Installed under `%LOCALAPPDATA%\AndroidForge\tools\maestro\2.12.1` (or the equivalent state directory).
- Requires Java 17+; AndroidForge points Maestro at the JDK it already discovered.
- Desktop **Setup → Environment** shows an **Install Maestro** button, a confirmation dialog with the
  pinned version/URL/hash/target, progress, the active path and Copy path. CLI-installed copies are
  detected automatically.
- Maestro remains **best-effort/optional**; the installer pins one tested version.

### Desktop Tool database

A new sidebar page under **Workspace**, next to Setup, opens a complete command database generated from
the same clap parser the CLI uses:

- Search command paths, summaries, argument names and help text.
- Sort A-Z or Z-A.
- Rows show tool name, safety class and a concise summary.
- Click a row for a full detail page with bold title, usage, examples, argument table, possible values,
  defaults, safety classification and generated MCP tool name.
- Opening a tool uses a short slide/fade transition.
- The catalog comes from `androidforge tools catalog --json`; it cannot silently drift from the CLI.

### Complete MCP surface

`androidforge mcp serve` now exposes **192 tools**:

- Curated safety-reviewed tools keep their friendly schemas (`androidforge_app_install`,
  `androidforge_ui_tap`, etc.).
- Every other bounded, non-unsafe CLI leaf command is generated as `androidforge_<command_path>` from
  the catalog. Raw `adb`/`run exec` and the nested `mcp serve` are excluded; `network mock serve` is
  exposed only through the bounded curated tool.
- Generated tools use the CLI argument names and safety classes.
- Mutating generated tools require `confirm=true`.
- Physical mutation cannot be self-approved from the MCP JSON object; the CLI/user must make that
  decision outside the tool call.
- Raw `adb` and `run exec` are classified **unsafe** and deliberately excluded from the generated MCP
  surface. They remain available to a human/CLI that intentionally invokes them.
- `androidforge://catalog` exposes the full command catalog as an MCP resource.
- `tools/call` has a 600-second wall-clock limit, bounded stdout/stderr and process-tree termination;
  JSON-RPC request lines are capped.

### Compatibility and deprecation policy

[`COMPATIBILITY.md`](https://github.com/JuggyBob/AndroidForge/blob/v0.13.0/COMPATIBILITY.md) now defines:

- Stable tiers for commands/flags, JSON envelope, error and exit codes, report schema, curated MCP
  tools, generated MCP tools and internal state.
- The semantic-versioning and deprecation window.
- Additive-field rules and how to report a compatibility problem.
- What is explicitly not covered (human formatting, internal Rust APIs, best-effort parsers).

`tools-catalog.schema.json` documents the command catalog shape.

### Security-hardening pass

This release closes findings from five independent security audits, including a final regression audit:

- MCP `tools/call` now enforces the advertised tool set; hidden unsafe/long-running catalog entries
  are rejected before argv construction. This closes a pre-release regression where the hidden
  `androidforge_adb`/`androidforge_run_exec` names were still callable.
- Generated MCP tools forward array-valued `serial` targets (for example `agent matrix`), and
  `report prune`, `app data-restore` and `doze unforce` now require `confirm=true`.
- MCP `tools/call` execution is bounded to 600 seconds with output caps and process-tree termination.
- Fail-closed device classification: only `emulator-*` serials are unprotected emulators; unknown/vendor
  devices require `--allow-physical-mutation`.
- Physical guards added to app launch, broadcast, service, force-stop and kill.
- Package names validated before `run-as`/external path interpolation; `..` cannot escape the app
  directory.
- App-data tar restore rejects absolute/parent paths, symlinks, devices and non-regular entries.
- Session GC refuses to reclaim a stale session with a live emulator or operation unless `--stop`.
- Mock server gets per-connection timeouts, a 64-connection cap, exact body slicing, CRLF header
  validation, expanded sensitive-header redaction and redacted body logs.
- Maestro installer cleans up staging on failure; desktop update staging is random and size-capped.
- Desktop CLI output/preview frames are bounded; run paths must contain `report.json`.
- Desktop Maestro install now goes through the normal confirmation dialog.

## Fixed

- MCP could previously expose `run exec` and raw `adb` as unconfirmed "read-only" tools. They are now
  unsafe and excluded.
- MCP physical mutation could be self-approved with `allow_physical_mutation=true`. That field is no
  longer generated or forwarded.
- Stale session GC could free a live emulator lock.
- Package/path traversal in `--external` file push/pull.
- Mock request bodies could appear unredacted in NDJSON logs.
- Predictable update/Maestro staging directories.

## Validation

- Full workspace test suite, strict clippy and formatting via the delegated release gate.
- `tools catalog`: 191 commands; `tools schema --format mcp`: 192 tools.
- Maestro install/status/uninstall in an isolated home; doctor reports `2.12.1` and the managed path.
  A passing flow and a deliberately failing flow ran on a disposable API 36 emulator; both reported
  `result.version:"2.12.1"`, failure exit `6`, and preserved evidence.
- Mock HTTP/TLS/redaction/timeout smoke; MCP generated tool calls; 15-page desktop smoke; multi-emulator
  and physical session-ownership campaigns recorded in `VERIFICATION.md`.
- Physical Xiaomi POCO X4 GT: install, `verify-installed`, live status hash, same-version
  `--only-if-changed` (`reason:content_different`), UI dump/find/tap, screenshot, 5s recording,
  out-of-band refresh, uninstall only the isolated test package. Baseline `22DDD58E…`, modified
  `198A1EF3…`, same certificate.

## Compatibility and upgrade

- Workspace, CLI, desktop, installer and compatibility version are `0.13.0`.
- Report schema remains `1`; v0.12.x reports remain readable.
- Existing command names, JSON envelope, exit codes and session ownership are preserved.
- New fields, schemas and MCP tools are additive; raw `adb`/`run exec` are no longer auto-generated MCP
  tools.
- The desktop and CLI must both be `0.13.0`.
- The desktop visual system is unchanged from v0.11.0; the v0.11.0 screenshot gallery remains
  representative.

## Known limitations

- Maestro remains optional/best-effort. The installer is Windows-only and pins one tested version.
  Flows were validated on an emulator; physical-device Maestro flows remain unvalidated.
- Physical-device validation covers one Xiaomi debug package; vendor ROM behavior is best-effort.
- Maestro flows were validated on an emulator (pass and fail); a real instrumentation test APK was not
  validated.
- Snapshot restore, root-only time changes, macOS/Linux hosts and code signing remain unverified.
- Raw `adb`, `run exec` and physical mutation are deliberately excluded from MCP self-service.
- The Inno Setup installer is compiled and its version/payload/checksums are verified; a silent
  install/uninstall cycle was not run on the release host.
- The desktop is Windows-focused; binaries are unsigned.
